注意：电机内部闭环保证的是电机轴运动；轮胎打滑、横移误差和车身偏移，仍需小车层面的定位修正。

## 4. 大头电机怎样驱动轮子

主要位置接口：`Emm_V5_Pos_Control(addr, dir, vel, acc, clk, raF, snF)`。

| 参数 | 本代码含义 |
| --- | --- |
| addr | 总线电机地址；底盘 1～4，升降 5 |
| dir | 0 / 1 表示两种电机旋转方向；与小车前后左右的对应关系取决于装配 |
| vel | 电机转速，RPM |
| acc | 8 位加速度档位；不是直接填入物理加速度 |
| clk | 命令脉冲数；不是毫米，也不是 MCU 在这里输出 PUL 脉冲 |
| raF | 0 为相对位置运动；现有行走调用主要取 0 |
| snF | 多机同步标志；现有行走调用取 0 |

源码发送的串口布局如下，多字节整数高字节在前：

| 动作 | 字节布局 |
| --- | --- |
| 位置 | `Addr FD dir speed[2] acc pulses[4] relative_or_absolute sync 6B`，13 字节 |
| 速度 | `Addr F6 dir speed[2] acc sync 6B`，8 字节 |
| 立即停止 | `Addr FE 98 sync 6B`，5 字节 |
| 同步触发 | `Addr FF 66 6B`，4 字节 |

这与云台 skill 中的 Emm 速度布局一致。X 固件虽然也使用 F6，但参数布局不同，不能直接替换。旧源码中“最高 5000 RPM”的注释不能当作实物额定范围；速度上限需对应具体型号和固件手册核对。

现有 car() 的方向模式如下。表中的序列是地址 1、2、3、4 的 dir 参数，先保留代码定义，不擅自命名实物前后左右。

| car 的 dir | 各电机方向 | 特征 |
| --- | --- | --- |
| 1 / 2 | 0101 / 1010 | 一组互逆平移 |
| 3 / 4 | 1100 / 0011 | 另一组互逆平移 |
| 5 / 6 | 1111 / 0000 | 两种旋转方向 |
| 7 / 8 | 仅 2、3 号参与；10 / 01 | 两轮参与的互逆运动 |
| 21 / 22 | 与 1 / 2 相同 | 带约 3 秒等待超时的工位微调版本 |
| 10 / 11 | 1010，但 1、3 与 2、4 行程不同 | 为原路线写死的转弯组合，内部速度固定 500 |
| 0 | 用速度模式修正航向 | 第二个参数在这里是目标角度，不再是速度 |

四轮命令依次发送，各命令间延时约 10 ms；同步触发调用被注释，当前不能称为四轮同步启动。路线大量使用 `1850*4`、`19000*4` 等经验行程，不能仅凭乘 4 推断细分数、轮径或减速比。

## 5. 视觉和姿态控制现状

- UART4 坐标格式是 `A3 B3 x y`，x、y 各 1 字节。STM32 使用 `error_x=122-x`、`error_y=49-y`。
- `vision()` 按误差正负用低速速度模式调整两轴，在一定误差范围内停止。当前有效逻辑不是完整的连续二维 PID。
- `WL_dingwei()` 等待相对稳定的坐标，将像素误差按经验系数转换为电机脉冲，再执行位置微调。虽然外层写了循环，内部 `flag_n==1` 就返回，实际只执行一轮修正。
- 第一件取料使用视觉坐标定位；后续物料会发送字符 7、8、9，并等待缓冲区首字节出现 A4、A5、A6。这里缺少独立、完整的事件帧解析，实际语义应结合摄像头程序核对。
- 姿态中断输出 `global_angle`，TIM2 中断调用 `angle(global_angle,0,0)`。当前 angle() 的返回值为 int，因此 anglea 实际是整数化角度，不应误认为它就是已调好的车轮 PID 输出。
- 未发现摄像头端 Python 程序。不能从 openmv.c 推断完整的颜色阈值、镜头安装方向、像素与距离标定或原颜色编号含义。

## 7. 后续修改前应先处理的代码问题

1. **到位消息没有按电机归属管理。** car.c 多处只检查 `rxCmd[1..3] == FD 9F 6B`，不检查地址、长度或四轮是否全部完成。5 号升降和四轮共用这个缓冲区，存在跨电机误认完成的条件；长短行程转弯也可能被较早到位的一轮提前放行。
2. **大部分动作阻塞且没有统一超时。** 多个 car、vision、等待物料分支会一直循环。car 的 21、22、6 有局部超时，但超时后只退出，未向上层区分正常完成和失败。
3. **电机接收以串口空闲划分数据块。** 多个回复可能落在同一块或被拆分，业务却只看缓冲区开头。没有看到完整的逐帧归属、负响应处理及周期状态读取。
4. **航向修正退出条件不完整。** `anglea==speed || anglea==179 || anglea==-179` 允许任何目标角度在 ±179 度退出；也没有通用角度容差、跨 ±180 度误差归一化、姿态失联超时。两个转向判断还是独立 if，边界时可能先后发送相反方向。
5. **视觉缺少新鲜度管理。** 坐标帧没有序号、有效标志、校验和接收时间；旧坐标可持续影响速度命令。vision 的 flag_n 要求先发生过修正，目标一开始就在容差内时可能一直等待。
6. **加速度参数截断。** wuliao.c 和 task.c 将若干升降加速度变量设为 500，但 Emm 接口 acc 是 uint8_t，传入后实际变为 244。不能将这些变量直接理解为实际发送的数值。
7. **扫码接收缺少边界和完整解析。** `saoma_data[cnt++]` 没有限长和重置逻辑；主任务未先确认有效完整任务码就开始路线。显示发送放在 UART5 中断中，也增加中断占用。
8. **两套 SysTick 用法需要统一。** delay_ms() 直接改 SysTick 寄存器；舵机库倒计时使用 sysTickCnt，但现有 SysTick_Handler 为空。若后续启用依赖倒计时的舵机查询或等待，超时无法按预期递减；不能把它直接当作可靠系统时间。
9. **机械动作常以固定延时作为完成依据。** 当前转轴和夹爪调用串口舵机时 wait=0，抓取成功、物料落座和放置正确也没有对应确认。新增统计不能仅凭调用过一次函数就判定成功。

上述结论来自静态代码，不表示这些异常已经在实车上复现。用户提供的“旧版正常行走”与这些改造时需要关注的边界条件并不矛盾。

## 8. 推荐的后续开发顺序

1. 保留学长工程作为可对照基线，核对轮号、方向、轮径、细分和脉冲距离标定，以及实物主控、晶振、电机型号和固件。
2. 先把电机通信变为按 1～5 号地址分别管理收发和完成状态，让动作返回完成、超时或失败。
3. 将行走改成能够周期检查传感器、暂停和停止的任务过程，保留已走行程或可靠的位置估计。绕障后重新定位或重新规划，不能简单把原段完整脉冲重发。
4. 在正常路线执行和底盘控制之间加入障碍检测、可通行空间判断、绕行和路线恢复。400 mm 通道内是否能侧绕需考虑车宽、障碍位置及车体转动后的投影，不能只看车中心是否越界。
5. 保留“站间移动 + 到站视觉精调”的整体思路，同时加入连续定位修正与视觉失联处理。
6. 把任务码解析为两批颜色顺序及位置数组，用数据驱动抓放流程，替代大量 1、2、3 排列分支；再接入经过确认的成功统计。

云台 skill 可复用的是大头电机协议核对方法、回复归属、新鲜度和超时处理、分层控制思路。车轮控制、五电机总线调度、场地定位与避障需要针对本项目实现；本次没有修改云台 skill 或生成替代工程。

后续还需要实物信息：各轮地址与安装方向、电机具体型号及固件、总线电气接口、轮径/减速比/细分、底盘长宽、摄像头型号与端上程序、姿态模块型号、扫码及显示设备接法、准备使用的避障传感器。
