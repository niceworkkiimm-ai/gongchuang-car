# 扫码模块 → STM32 UART5 → 串口屏

本修改基于你提供的“小车只加通信版本 (2)(1).zip”。仅修改工程中的 hardware/uart_5.c，其他 97 个 C/H/汇编/Keil 工程文件与原 ZIP 逐字节相同。原 ZIP、原桌面工程和 HMI 文件未覆盖。

## 使用

- 在现有工程中只替换 hardware/uart_5.c 后重新编译；或直接打开本包内 小车只加通信版本/PRJ/STM32_UART_CMD.uvprojx。
- Keil 目标 STM32_PUL_WHILE，STM32F103ZE，ARMCC 5.06 update 5 build 528。
- 完整工程已生成 PRJ/Objects/Template.hex，仍包含原有小车动作流程。
- 屏幕程序保持现有 page0.t0 文本控件，不需要为本修改增加屏幕接收代码。

## 接线与格式

| 信号 | 接线 |
|---|---|
| 扫码模块 TX | STM32 PD2 / UART5_RX |
| 屏幕 RX | STM32 PC12 / UART5_TX |
| 屏幕 TX | 不连接 PD2，不与扫码模块 TX 并接 |
| 地线 | STM32、扫码模块、屏幕共地 |
| 串口参数 | 三方均 9600，8 数据位，1 停止位，无校验 |

屏幕识别的扫码内容为七个 ASCII 字符：前三位各为 1~6，中间 +，后三位各为 1~3。例如 162+132、456+321。沿用原七字节滑窗，兼容 CR、CRLF、DT 或无后缀。

扫码得到 162+132 后，PC12 发出 25 字节：

    page0.t0.txt="162+132" + FF FF FF

最后三个 FF 是原始十六进制字节 0xFF，不是字符串“FF FF FF”；不发送字符串结尾的 NUL。9600 波特率下整帧约 26 ms，使用 TXE 中断逐字节发送，不在中断里等待整帧。

## 保持原功能的边界

- saoma_data / saoma_ready 仍只接收并锁定上电后第一组全部数字 1~3 的扫码。原运动流程、其他串口、OLED、main、delay 都没有改。
- 162+132 可以显示，但不会使原运动流程的 Scanner_WaitForData 返回；此前没有有效 1~3 任务数据时，小车到原扫码等待位置后仍会等待。这是按本次“只改显示，保留原运动规则”的要求处理。
- 任务数据锁定后，屏幕仍可以显示后续扫码；屏幕上的最新值不代表已更改小车锁定的物料顺序。
- 发送过程中收到新扫码时，先发完当前帧，再发最新待发值。扫码密集程度超过显示发送速度时，可跳过中间值，但不拼接混合帧。
- 屏幕应启动完成后再扫码。屏幕单独重启后请重新扫码；屏幕 TX 未连接，STM32 无法确认屏幕是否实际显示成功。

## 上板验收

1. 屏幕启动完成后扫码 162+132，page0.t0 应显示 162+132。
2. 再扫 456+321，应更新显示。
3. 检查 123+321 仍按原规则锁定任务；后续扫其他内容，屏幕可更新，但运动任务数据不变。
4. 不应把 762+132、162+432、含 0 或其他符号的七字符内容识别为本次规定的格式。
5. 若串口助手模拟扫码，向 PD2 输入的是 162+132 原始文本，不是屏幕指令；通过 PC12 抓取的输出才是上述带 FF FF FF 的屏幕指令。
